Private Wine clearance pipeline

This flow follows the supported private Wine model through its recorded checks, native assessment and separate agency review. Conventional models use their own ordering and evidence requirements. Reading this map does not execute jobs.

  1. Choose Wine

    Select the bundled Wine dataset and its private categorical preset. This fixed example does not qualify a dataset or private agency inputs.

  2. Freeze the plan

    Before fitting, record the fixed recipe, privacy mechanism, recipient interface, prospective policy and evaluation design.

  3. Train a private model

    Fit the categorical model using secret OS randomness and noisy counts. Each new training release needs its own disclosure accounting.

  4. Export and reload

    Save the exact model-only recipient package and check its predictions after reload. Keep operator audit material separate.

  5. Run checks, then replay

    Utility, attacks and controls

    Record utility, compatible real attacks, positive/null controls and unsupported checks. These exploratory measurements do not supply a privacy ceiling.

    Privacy mechanism and verification

    Then replay the accountant and model postprocessing, and verify source, candidate and evidence bindings against the frozen scope and exact recipient package.

  6. Native assessment

    Submit the verified, admissible evidence to the assessment engine. Clear, block or inconclusive is a scoped scientific outcome, not release authority.

  7. External agency review

    Agency owners and independent reviewers must resolve authority, remaining risks and deployment controls outside this demo. Local government review notes retain gaps; they do not perform that acceptance.

Keep the packages separate. The verified recipient model is the exact model-only package covered by this private example. The operator evidence ZIP also retains audit material and is outside that recipient claim. Neither download grants agency release authorization.

01 · UNDERSTAND THE OUTCOME

Why do the trained models say inconclusive?

A model run answers several different questions. Did training finish? Which attacks ran? What did they measure? Is there enough correctly scoped evidence to support the registered assessment? These answers can differ.

The conventional public-data walkthrough records attack measurements and a narrow registered, loss-based membership assessment. In the eight earlier trained-model examples inspected on 7 October 2026, the policy tolerates a true-positive rate of 0.20 at a target false-positive rate of 0.10. None has admissible evidence establishing a clearing bound for the complete recipient interface. Their decision ceiling remains 1.0, above the tolerance, so the policy returns inconclusive.

A finite attack can demonstrate a weakness, but a weak or unsuccessful attack does not bound every attacker's success. For example, the saved ACS/random-forest attack attained the declared false-positive target, with a membership floor of about 0.0774 and a false-positive upper bound of about 0.0956. Its floor below 0.20 still does not supply a clearing ceiling. Other saved examples did not attain that false-positive target; their registered floors remain zero. Optional agency documents, government checklist gaps and an unsupported tree check do not cause this membership verdict.

Open a recorded run and read Why this assessment is inconclusive for its retained reasons, bounds and operating-point check. Select Download assessment report JSON for the original decisions and evidence references. In Red-team tools, expand each tool's details to see the attack, baseline, budget and limitations. The findings remain useful even when the overall assessment cannot reach a supported conclusion.

Do not change a threshold just to make the result green.

Choose the threat, policy threshold and evaluation plan before collecting assessment evidence. The current policy requires admissible exact complete-interface evidence for a clearing decision; its ceiling_prohibited setting does not accept ceiling-only clearance. Adding documents, running more exploratory attacks or repeating training does not create that evidence. Plan prospective registered evidence and agency-approved criteria; narrow the recipient interface where scientifically justified. Changing the policy requires a legitimate approved decision and its required evidence battery, rather than a cosmetic threshold change. New inputs belong in a new recorded attempt. Use the synthetic scenarios below to explore different decisions without relabelling a real run.

02 · INSTALL AND START

One launcher starts the web service and worker

  1. Download the ZIP. Save Try-Demo.zip on Windows x64.
  2. Extract and double-click. Use Extract All, then double-click Try-Demo.cmd in the extracted folder. No Git, preinstalled Python or administrator installation is required. First use needs internet access for the managed runtime, fixed application snapshot and console packages.
  3. Wait for dataset checks. Setup validates and prepares local copies of all four required public samples: Wine, Digits, Breast Cancer and Diabetes, bundled in scikit-learn 1.6.1. The launcher then starts the web service and separate worker and opens the browser.

The plain launcher is also available. If the browser displays the script, use Save as and retain the filename Try-Demo.cmd rather than .txt.

Open http://127.0.0.1:8765/ if the browser does not open. Keep the launcher window open; Ctrl+C stops both services. If Windows asks Terminate batch job (Y/N)?, confirm with Y. Later launches validate and reuse the installation. The core public-data examples run offline after setup.

The default home is D:/MRA-Demo/<Windows username> when D: is available, otherwise %LOCALAPPDATA%/MRA-Demo/<Windows username>. Runtime, application, prepared data and new evidence stay under that home. OneDrive locations are refused. This remains a trusted local, loopback service.

The bootstrap uses official portable CPython NuGet 3.13.16 and the immutable source snapshot pinned in the downloaded Try-Demo.cmd. Installed dependencies are checked against requirements; they are not described as a completely locked dependency set.

Standalone Windows settings and optional existing research inputs

Use MRA_DEMO_HOME for another absolute home outside OneDrive, MRA_DEMO_PORT for another port, MRA_DEMO_SETUP_ONLY=1 to prepare without starting services, or MRA_DEMO_NO_BROWSER=1 to start without opening the browser.

# PowerShell, beside the extracted launcher
$env:MRA_DEMO_RESEARCH_DATA_ROOT = 'D:/model_audit_data'
& .\Try-Demo.cmd

The research root is optional and must already contain the four fixed historical prepared matrices. No large raw collection is downloaded or missing source replaced. The research inputs and new console evidence have different roles.

Advanced existing checkout or Linux/macOS setup

With Git and Python 3.11 or newer, clone outside synchronized storage and use the source launcher:

git clone https://github.com/elmontu/AI_ModeL_Check.git
cd AI_ModeL_Check
python scripts/start_demo.py
# On Linux/macOS, use python3 instead.

This route keeps its environment and evidence under .local/demo-venv and .local/demo-data. Add --research-data-root D:/model_audit_data for existing research sources or --data PATH for another evidence directory.

03 · DATASET FIRST

Choose from eight dataset profiles

Dataset overview is the main view. In the current source checkout, the default Graph connects each dataset to every saved training run or attempt, then to that run's recorded training assessment. Runs stay separate by job ID, so multiple models remain visible. Unfinished attempts do not imply a trained model exists. Dataset nodes have no verdict; assessment nodes retain the original training result rather than a later case assessment. Older standalone launcher snapshots may predate the graph; download the current launcher to get the latest included view.

Choose Cards for the catalog view. Both views share the Source filter: Local research or Bundled examples. In Graph, Find a dataset or model searches by dataset, model family or short job ID; Training runs filters run state. Use Zoom graph in (+), Zoom graph out (−) and Reset view. Click a node, or use Tab and Enter, to open its dataset or run details. A selected run offers Inspect model run, Red-team results and, when its saved case exists, Review model case.

In Cards, View dataset → opens the same dataset details. Select Train a model to open the wizard with that dataset selected. The graph only reads retained observations; it does not verify current source bytes, start jobs or authorize release. Model results do not qualify their dataset.

The first four datasets are bundled with scikit-learn. Research selections need the configured source root. Each uses the retained 27,000-row prepared matrix, then a fixed-seed sample of at most 4,096 rows; the console does not train on the entire raw source collection.

The research loader expects experiments/mixed-model-export-20260929-v1/<corpus>/data/data.npz and manifest.json below the source root. A configured source is checked when a run starts; an overview entry or older provenance record does not verify its current bytes. Missing or changed files fail the run, with no automatic download or replacement dataset.

05 · REAL MODEL AND CLEARANCE EVIDENCE

Train with evidence that can establish clearance

Under More guided workflows, select Open private-training wizard in Train with clearance evidence. It selects Wine classification and Private categorical model: Wine membership clearance. Review the fixed scope and select Start training once.

This trains a real categorical Naive Bayes model using fixed alcohol/proline bins and noisy counts. Before fitting, the worker freezes the recipe and prospective policy. It then trains with secret OS randomness, independently replays the privacy calculation and model postprocessing, runs compatible real attacks and known-leak/null controls, and submits the evidence to the native assessment engine.

What does this clear result cover?

The conservative privacy parameter is epsilon ≤ 1/3, delta 0 for add/remove-record adjacency. It gives a membership TPR ceiling of approximately 0.13957 at FPR 0.10, below the unchanged tolerance 0.20. Clearance covers the exact model-only recipient package and one training release. Utility, other threats, person-level groups, prior models and operator evidence are outside this claim. Agency release authorization is not granted.

  1. Open the completed run and read Scientific clearance within the recorded scope. Inspect its bound, protected unit, recipient files, evidence assumptions and policy.
  2. Select Download verified recipient model for the inert JSON model package. The endpoint checks the retained evidence again and refuses missing or changed bytes. The operator evidence ZIP is a separate audit package.
  3. Select Open trained model case, then Check inputs and Run assessment. Preflight verifies the private evidence before creating another retained assessment.
  4. Read held-out utility, real attack metrics, both independent controls and unsupported checks separately. Fresh noise can change utility. Do not treat repeated training releases as free privacy refresh; they require composition.

The new local policy explicitly waives institutional attack-battery qualification for this mathematical mechanism example; that reason is retained in the assessment. Local controls do not authenticate agency acceptance. The eight earlier conventional-model cases retain their original verdicts.

Use the complete recipe, replay and recipient inference guide ↗ for the exact sampler, accountant and command to predict from the package. The one-release guarantee begins at valid training input records; private ingestion, population selection and cumulative disclosure still need qualification.

06 · RED-TEAM WORKSPACE

Read tools, metrics, controls and gaps together

  1. Open Red-team tools. Choose Dataset for red-team tools and the exact Recorded model run.
  2. Read each named card's execution state and measured values. Expand the card for full details. Check member/nonmember cohorts, query budgets, perturbation settings and baselines.
  3. Inspect coverage gaps and unsupported tools. Use the run/evidence actions to review the source report and retain the full measurement values.

Train and run checks opens the wizard for the selected dataset. It trains a new model and runs compatible checks automatically. It does not rerun only one attack against an existing model. A dataset with no recorded run has no measurements yet.

Classifier tools

Structural disclosure; learned membership attack; loss/confidence/entropy membership; model extraction; attribute inference; numeric perturbation; label-only membership; adaptive adversarial search; tree-leaf exposure; label poisoning; trigger backdoor.

Regression tools

Regression loss membership, regression extraction and regression perturbation. Classification-specific tools are not silently treated as completed regression checks.

Compare extraction agreement with its majority baseline, inference accuracy with its baseline, perturbations with clean utility, poisoning with a clean retrain, and trigger success with the clean-model trigger baseline. Check attack AUC alongside dummy controls and the registered operating point. A larger or smaller metric only has meaning under that tool's recorded definitions.

The integrated tools are exploratory measurements. The registered assessment uses its own bound evidence and policy; it does not convert every completed card into a release verdict. For example, tree-leaf exposure is unsupported on Wine/logistic. Keep that gap visible.

Separate integrations and release workflow

SACRO-ML, ART, garak, PyRIT, public export screening and multi-shadow experiments have separate documented workflows. Separate tool integrations lists their boundaries; catalog discovery does not install or execute them. The temporal dashboard at port 8767 is also separate and does not automatically import console cases or results.

07 · OPTIONAL LANGUAGE TESTING

Test an already installed Ollama model

In Red-team tools, select Test an installed language model. Choose an Installed Ollama model, then select Run local tests. The demo does not install or download a model.

The job runs nine synthetic probes and two controls: direct secret extraction, instruction override, role spoofing, encoded extraction, fragment extraction, retrieved-document injection, answer contamination, inert tool-call injection and multi-turn pressure. Retrieved documents and secrets are synthetic. Tool requests are inspected and never executed.

Read observed violations, both controls, failed probes and limitations in the run details. “No match detected” means the detector found no configured match in that finite probe; it is not a guarantee against prompt injection or data leakage. An offline provider or failed probe can leave coverage incomplete.

08 · CASE AND GOVERNMENT REVIEW

Keep input checks separate from evidence adequacy

Open the training run and select Open trained model case, or open its case from the dataset details. Check inputs checks required bindings. Run assessment assesses the current bound inputs; it creates another retained run.

Training creates an Education case. Candidate, lineage, request, evaluation plan and utility report are bound. Agency scope, security report and independent review remain optional for exercises. Use review mode requires all eight slots, but supplying files does not prove their truth or scientific adequacy. Changing mode or bindings can make earlier review entries stale.

Select Government audit review in the case. For each of the twelve controls, choose Evidence recorded, Gap identified or Not applicable, explain your rationale and save. Evidence-recorded entries require an unchanged bound file; the server verifies those bytes, not whether the document answers the question.

The twelve review controls
  1. Purpose, omission and utility
  2. Privacy adjacency
  3. Complete recipient package and history
  4. Training and scoring footprints
  5. Cache reuse and attribute versions
  6. Protected information flow
  7. Cumulative accounting
  8. Derivative and component lineage
  9. Joint attacks and uncertainty
  10. Exact-byte commit and delivery
  11. Expiry, revocation and recovery
  12. Agency decision and remaining risks

Not started means unanswered. Needs work marks a gap or stale context. Recorded means a current entry was stored, not a scientific pass or institutional approval. Use Refresh evidence after changes, and retain Download review JSON alongside the run evidence.

09 · RETAIN THE PACKAGE

Download reports and the exact run artifacts

In run details, use Download result JSON and Download evidence ZIP. The ZIP includes generated artifacts and a SHA-256 manifest. Assessment bundles include audit and preflight reports. Failed attempts can retain partial artifacts and diagnostics; inspect those too.

ZIP bundles are limited to 64 MiB. Larger evidence can be downloaded file by file from the artifact inventory. External case input bindings stay at their original paths and are not copied into the ZIP. The government review JSON is a separate checklist, so download it separately.

Keep the job ID, dataset and preset, source provenance, evaluation plan, result, model artifacts and review together. A retry has a new ID linked to the original; previous results stay intact. Generated evidence may contain model or source-derived information. Choose what to share before publishing files.

10 · SEE DIFFERENT DECISIONS

Use the eight synthetic reference scenarios

Under More guided workflows, select Run scenarios on Explore decision scenarios. The worker runs eight fictional fixtures covering evidence gaps, demonstrated leakage, tampering and lifecycle changes. Inspect their individual results and downloaded reports.

These fixtures demonstrate decision branches under predefined synthetic evidence: CONTINUE_TO_EXTERNAL_REVIEW for a scoped clear control, HOLD for missing evidence, BLOCK_AND_REDESIGN for demonstrated leakage, STOP for tampering or mismatch, REASSESS for stale evidence, and SIMULATED_ACTIVE / SIMULATED_SUSPENDED for mocked lifecycle controls. These are eight scenario results, not eight trained models or deployed releases. A synthetic passing branch does not imply a public-data model should pass. Open an existing Reference scenarios entry in Run history to inspect its retained result, or use Run scenarios to create a fresh attempt.

11 · SESSION AND STORAGE

Stop services without discarding evidence

Press Ctrl+C in the launcher terminal to stop the web service and worker. If Windows asks Terminate batch job (Y/N)?, confirm with Y. Cases and results remain in the selected data directory. Reopen Try-Demo.cmd with the same installation home and research setting for the standalone Windows route. For a source checkout, use the same --data value and research-root option. Queued jobs persist; interrupted jobs retain their attempt history and recovery state.

Standalone setup-only mode uses MRA_DEMO_SETUP_ONLY=1. The following commands apply to an existing source checkout:

# Prepare the environment without starting services
python scripts/start_demo.py --install-only

# Use another local port
python scripts/start_demo.py --port 8766

# Keep new evidence and existing research inputs on D:
python scripts/start_demo.py --data D:/YOUR_LOCAL_EVIDENCE_FOLDER --research-data-root D:/model_audit_data

Use python scripts/start_demo.py --help for --venv and --wheelhouse. On Linux/macOS, use python3 and an existing absolute local source path. Selecting a new evidence directory shows a different workspace; it does not migrate prior records.

13 · AGENCY PRIVATE CLOUD

What remains before a production deployment?

The production direction is an agency private cloud with provider and region still open. The framework is sector-neutral; a major public-health agency is one possible use case. The local public-data demo is assessment and engineering practice, not qualification of the agency's large private datasets.

A production pilot needs an accountable agency, purpose, data classification, recipient and model profile; authenticated identities and permissions; immutable classified data custody; isolated workers and quotas; reviewed privacy mechanisms and complete training/scoring dependencies; representative independent evidence; authoritative prior-disclosure accounting; and an enforcing delivery path. Operations must prove monitoring, incident response, restoration, retention and capacity at the approved scale.

Private-cloud hosting and more attack tools do not supply membership privacy, whole-record privacy or a lifetime citizen-privacy guarantee. The applicable scientific scope and unresolved threats must be accepted through the agency's actual review process. Local checklist entries and demo results do not issue release authority or deploy a model.
